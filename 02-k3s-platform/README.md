## Architecture

### Proxmox Host

- CPU: 6-core Xeon
- RAM: 128 GB
- Storage: `local-lvm` (LVM thin pool)
- Network: VLAN-aware bridge (`VLAN`), carrying tagged VLAN 200

### Control Plane Nodes — etcd quorum + k3s API server

| Name | VM ID | IP | vCPU | RAM | Disk |
|---|---|---|---|---|---|
| k3s-control-01 | 201 | 192.168.200.10 | 2 | 4 GB | 32 GB |
| k3s-control-02 | 202 | 192.168.200.11 | 2 | 4 GB | 32 GB |
| k3s-control-03 | 203 | 192.168.200.12 | 2 | 4 GB | 32 GB |

### Worker Nodes — workload scheduling

| Name | VM ID | IP | vCPU | RAM | Disk |
|---|---|---|---|---|---|
| k3s-worker-01 | 204 | 192.168.200.20 | 2 | 16 GB | 80 GB |
| k3s-worker-02 | 205 | 192.168.200.21 | 2 | 16 GB | 80 GB |

**All VMs:** CPU type `host` (passthrough), CPU units `512`, `qemu-guest-agent` enabled, `on_boot = true`, `discard = on` (LVM thin provisioning), cloud-init user `ansible`.

> **CPU units 512:** Proxmox uses CPU units as a relative scheduler weight. Setting k3s VMs to 512 (vs the default 1024) gives the management VM scheduling priority during contention, preventing noisy-neighbour issues on a shared host.

### Network Architecture

```
Management Network
        │
        ▼
  pfSense firewall
        │
  inter-VLAN routing
        │
  VLAN 200 — 192.168.200.0/24
  Gateway / DNS: 192.168.200.1 (pfSense unbound)
        │
  Proxmox VLAN-aware bridge (bridge: VLAN)
    ┌───┴───┐
    │       │
Control   Workers
.10 .11   .20 .21
.12
```

- pfSense manages inter-VLAN routing between the management network and VLAN 200
- All k3s nodes resolve DNS via the pfSense unbound resolver at the gateway IP
- Inbound traffic to nodes is restricted to explicitly allowed UFW ports only

## Phase 1 — Cloud-Init Template (Proxmox Host)

Run these commands directly on the Proxmox host as root. This creates VM ID 9000 — the Ubuntu 24.04 cloud-init template that all five nodes clone from.

### 1.1 Download Ubuntu Cloud Image

```bash
cd /var/lib/vz/template/iso

wget https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img
```

### 1.2 Inject QEMU Guest Agent and Truncate machine-id

```bash
virt-customize \
  -a noble-server-cloudimg-amd64.img \
  --install qemu-guest-agent \
  --truncate /etc/machine-id
```

**Why `qemu-guest-agent`?** The `bpg/proxmox` Terraform provider uses the guest agent to retrieve VM IP addresses after boot. Without it, Terraform cannot confirm the VM has initialised correctly and times out waiting for the agent heartbeat.

**Why truncate `/etc/machine-id`?** Every cloned VM must generate its own unique machine-id on first boot. If the template has a populated `machine-id`, all five clones inherit the same DUID — causing DHCP lease conflicts and preventing each VM from obtaining its own address, even when static cloud-init IP configuration is set. Truncating the file causes `systemd` to regenerate it uniquely on each clone's first boot.

### 1.3 Create the Template VM

```bash
# Create VM shell
qm create 9000 \
  --name ubuntu-2404-cloud \
  --memory 2048 \
  --cores 2 \
  --net0 virtio,bridge=VLAN

# Import the cloud image as a disk into local-lvm
qm importdisk 9000 noble-server-cloudimg-amd64.img local-lvm

# Attach disk as scsi0 with discard support for LVM thin provisioning
qm set 9000 \
  --scsihw virtio-scsi-pci \
  --scsi0 local-lvm:vm-9000-disk-0,discard=on

# Attach cloud-init drive on ide2
qm set 9000 --ide2 local-lvm:cloudinit

# Set boot order to scsi0
qm set 9000 --boot c --bootdisk scsi0

# Enable serial console (required by cloud-init for early output)
qm set 9000 --serial0 socket --vga serial0

# Convert to template (irreversible — creates a read-only base for cloning)
qm template 9000
```

### 1.4 Verify

```bash
qm list | grep 9000
# Expected: 9000  ubuntu-2404-cloud  template  ...
```

## Phase 2 — Terraform Provisioning

### Key Design Decisions

| Decision | Rationale |
|---|---|
| `bpg/proxmox` pinned at `0.66.3` | The provider has had breaking changes in minor releases; pinning prevents silent drift during `terraform init -upgrade` |
| `cpu.type = "host"` | Full CPU passthrough — exposes host instruction sets required by k3s eBPF dataplane and kube-proxy |
| `cpu.units = 512` | Proxmox scheduler weight; gives management VM priority over k3s nodes during CPU contention |
| `discard = "on"` | Enables TRIM pass-through to LVM thin pool — prevents disk over-provisioning on `local-lvm` |
| `for_each` over `locals` maps | DRY VM definitions; adding a node is a single entry in `locals.tf` with no changes to `main.tf` |
| Outputs sourced from `locals` | `control_plane_ips` and `worker_ips` are computable at `plan` time — the inventory generator does not require a completed `apply` |
| Azure remote state | Shared, locked state supports multi-operator workflows and prevents concurrent `apply` conflicts |
| `insecure = true` on provider | Proxmox uses a self-signed TLS certificate on its API endpoint |
| VLAN bridge without tag override | The bridge (`VLAN`) handles VLAN 200 tagging at the physical layer; `vlan_id = 200` in the network device block instructs the provider to tag frames correctly |

### 2.1 Initialise

```bash
cd terraform/
terraform init
```

### 2.2 Plan

Verify the plan shows **5 to add, 0 to change, 0 to destroy** and that each VM reflects the correct IP, memory, and disk size before proceeding.

## Phase 3 — Ansible Inventory Generation

The inventory is generated automatically from Terraform outputs — no manual IP editing required.

```bash
# From the 02-k3s-platform/ root
bash scripts/generate-inventory.sh
```

The script runs `terraform output -json`, parses it with `jq`, and writes `ansible/inventory/hosts.yml`:

```yaml
---
all:
  children:
    k3s_cluster:
      children:
        k3s_control:
```

### 4.4 Task Execution Order

The role asserts Ubuntu 24.04, then runs eight task files in order:

| Task file | What it does |
|---|---|
| `packages.yml` | Polls until `dpkg` lock releases; removes legacy packages (`telnet`, `rsh-client`); installs hardening tools; enables unattended security upgrades |
| `ssh.yml` | Deploys hardened `sshd_config` via template with `sshd -t` validation; strips DH moduli < 3072 bits; marks completion with sentinel file for idempotency |
| `ufw.yml` | Sets default deny inbound/routed, allow outbound; opens k3s-required ports; enables UFW |
| `sysctl.yml` | Deploys `/etc/sysctl.d/99-bls-hardening.conf`; applies immediately via `sysctl --system` |
| `limits.yml` | Sets 65536 nofile/nproc limits via PAM; ensures `pam_limits.so` active in common-session |
| `fail2ban.yml` | Deploys `jail.local` with UFW ban backend and SSH jail; enables and verifies service |
| `auditd.yml` | Installs auditd; ensures rules directory exists; deploys audit rules; loads rules live via `augenrules --load` |
| `ntp.yml` | Installs chrony; deploys UK NTP pool config; disables `systemd-timesyncd` to avoid conflicts |

## Security Hardening Reference

### SSH (`/etc/ssh/sshd_config`)

```
PermitRootLogin         no
PasswordAuthentication  no
PubkeyAuthentication    yes
AllowUsers              ansible
MaxAuthTries            3
LoginGraceTime          30
ClientAliveInterval     300
ClientAliveCountMax     2
X11Forwarding           no
AllowTcpForwarding      no
AllowAgentForwarding    no
PermitTunnel            no
```

**Algorithm policy (modern-only, OpenSSH 9.x on Ubuntu 24.04):**

```
KexAlgorithms      curve25519-sha256, curve25519-sha256@libssh.org,
                   diffie-hellman-group16-sha512, diffie-hellman-group18-sha512

Ciphers            chacha20-poly1305@openssh.com, aes256-gcm@openssh.com,
                   aes128-gcm@openssh.com

MACs               hmac-sha2-512-etm@openssh.com, hmac-sha2-256-etm@openssh.com

HostKeyAlgorithms  ssh-ed25519, ssh-ed25519-cert-v01@openssh.com,
                   rsa-sha2-512, rsa-sha2-256
```

DH moduli smaller than 3072 bits are stripped from `/etc/ssh/moduli`. A sentinel file at `/etc/ssh/.moduli_hardened` makes the task idempotent across subsequent playbook runs.

### UFW Firewall

Default policy: **deny inbound, deny routed, allow outbound.**

| Port | Protocol | Service |
|---|---|---|
| 22 | TCP | SSH |
| 6443 | TCP | k3s API server |
| 2379 | TCP | etcd client |
| 2380 | TCP | etcd peer replication |
| 10250 | TCP | kubelet metrics |
| 8472 | UDP | Flannel VXLAN overlay |
| 51820 | UDP | WireGuard (k3s optional encrypted overlay) |

### Kernel (`/etc/sysctl.d/99-bls-hardening.conf`)

```ini
net.ipv4.ip_forward                    = 1   # Required for k3s pod routing
net.bridge.bridge-nf-call-iptables     = 1   # Required for k3s
net.bridge.bridge-nf-call-ip6tables    = 1   # Required for k3s
net.ipv4.tcp_syncookies                = 1   # SYN flood protection
net.ipv4.conf.all.send_redirects       = 0
net.ipv4.conf.default.send_redirects   = 0
net.ipv4.conf.all.accept_redirects     = 0
net.ipv4.conf.default.accept_redirects = 0
net.ipv4.conf.all.log_martians         = 1
kernel.dmesg_restrict                  = 1
kernel.kptr_restrict                   = 2
```

`ip_forward = 1` is intentional — k3s requires it for pod-to-pod and pod-to-service routing. Setting it to 0 would harden the OS but break the cluster network.

### fail2ban (`/etc/fail2ban/jail.local`)

```ini
[DEFAULT]
bantime   = 3600   # 1-hour ban
findtime  = 600    # 10-minute observation window
maxretry  = 5
backend   = systemd
banaction = ufw    # Bans via UFW rules, not raw iptables

[sshd]
enabled  = true
port     = 22
filter   = sshd
```

### auditd (`/etc/audit/rules.d/99-bls-hardening.rules`)

Monitors:

| Event class | Key |
|---|---|
| `setuid` / `setgid` privilege escalation | `privilege_escalation` |
| `/etc/passwd`, `/etc/group`, `/etc/shadow` | `identity` |
| `/etc/sudoers`, `/etc/sudoers.d/` | `sudoers` |
| `/etc/ssh/sshd_config` | `sshd_config` |
| `/etc/cron.d/`, `/etc/crontab`, `/var/spool/cron/` | `cron` |
| `/var/log/faillog`, `/var/log/lastlog` | `logins` |

Rules are locked with `-e 2` (immutable until reboot) to prevent tampering by a compromised process.

### PAM Limits (`/etc/security/limits.d/99-bls-hardening.conf`)

```
* soft nofile 65536
* hard nofile 65536
* soft nproc  65536
* hard nproc  65536
```

Required for k3s and container workloads that open large numbers of file descriptors and threads under load.

### NTP (`/etc/chrony/chrony.conf`)

UK NTP pool (`0-3.uk.pool.ntp.org`), `makestep 1.0 3` to handle large initial clock drift on freshly booted VMs, `systemd-timesyncd` disabled to avoid conflicts with chrony.

## Troubleshooting Log

Issues encountered during Phase 4 and their resolutions. Documented for reproducibility and as reference for future cluster builds.

### Issue 1 — `packages_remove` / `packages_install` Undefined

**Symptom:** Role failed immediately on the first package task with `variable is undefined`.

**Cause:** Both variables were referenced in `packages.yml` task files but had no corresponding entry in `defaults/main.yml`.

**Fix:** Added both variables to `defaults/main.yml` with appropriate values:

```yaml
packages_remove:
  - telnet
  - rsh-client
  - rsh-redone-client

packages_install:
  - fail2ban
  - ufw
  - curl
  - wget
  - unzip
```

---

### Issue 2 — dpkg Lock Contention on Fresh VMs

**Symptom:** `ansible.builtin.apt` blocked indefinitely; `dpkg` returned a lock error immediately after VM first boot.

**Cause:** Ubuntu 24.04 cloud-init runs `apt-get` in the background on first boot (unattended-upgrades initialisation, snap daemon). Ansible connected to nodes within seconds of boot and encountered the lock before cloud-init's apt run completed.

**Fix:** Added a wait task at the top of `packages.yml` that polls until the lock is released:

```yaml
- name: Wait for apt lock to be released
  ansible.builtin.shell: |
    while fuser /var/lib/dpkg/lock-frontend >/dev/null 2>&1; do
      sleep 5
    done
  changed_when: false
  timeout: 300
```

---

### Issue 3 — DNS Resolution Failure on All Nodes

**Symptom:** `Temporary failure resolving 'archive.ubuntu.com'` on all five nodes simultaneously during `apt update`.

**Cause:** A stale NAT port-forward rule in pfSense was redirecting **all traffic destined for the gateway IP** (including DNS queries sent to unbound on port 53) to an external IP. Queries left VLAN 200 but were NATted before reaching the local resolver — unbound never received them.

**Diagnosis path:**

1. Confirmed unbound was running and listening on wildcard: `ss -ulnp | grep 53`
2. Confirmed access-control in `unbound.conf` allowed the VLAN 200 subnet
3. `tcpdump` on the pfSense VLAN 200 interface showed DNS queries arriving with no replies
4. Inspected `config.xml` — found a NAT rule with destination matching the gateway IP, redirecting all ports

**Fix:** Removed the offending NAT rule from pfSense under **Firewall → NAT → Port Forward**, then reloaded the ruleset:

```bash
# On the pfSense shell
pfctl -F nat
/etc/rc.filter_configure
```

**Lesson:** When DNS fails on a subnet where the resolver is confirmed running and access-control is correct, check pfSense NAT rules before spending time on resolver configuration. A NAT forward rule matching the resolver's own IP silently intercepts queries before they can reach unbound, regardless of any `access-control` directives.

---

### Issue 4 — Multiple Undefined Role Variables

**Symptom:** Several tasks failed with `variable is undefined` at different points across the run:

- `ssh_permit_root_login`, `ssh_pubkey_authentication`, `ssh_allow_users`
- `ssh_login_grace_time`, `ssh_client_alive_interval`, `ssh_client_alive_count_max`
- `ufw_allowed_ports` — missing `comment` field causing Jinja2 key error
- `sysctl_settings` — defined as a list; template iterates `.items()` expecting a dict
- `limits_settings`, `fail2ban_ignoreip`, `ntp_servers`, `auditd_rules_dir`

**Cause:** The role's templates and task files expected these variables, but `defaults/main.yml` was incomplete from the Project 1 import. The `sysctl_settings` format mismatch (list of `{name, value}` dicts vs flat key/value dict) caused a template rendering error even when the variable existed.

**Fix:** Added all missing variables to `defaults/main.yml` with k3s-compatible values. Changed `sysctl_settings` from a list structure to a flat dict to match the template's `{% for key, value in sysctl_settings.items() %}` iteration.

**Note on `ip_forward`:** `net.ipv4.ip_forward = 1` is set intentionally — k3s requires IP forwarding for pod-to-pod and pod-to-service routing. Without it, the control plane starts but all cluster networking fails.

### Issue 5 — auditd and chrony Not Installed

**Symptom:** Tasks in `auditd.yml` and `ntp.yml` failed with *"Destination directory does not exist"* when attempting to deploy rules files and configuration.

**Cause:** The original role assumed `auditd` and `chrony` were pre-installed on the base system. The Ubuntu 24.04 cloud image ships with neither by default.

**Fix:** Added explicit install and directory-creation tasks at the top of each file:

```yaml
# auditd.yml
- name: Install auditd
  ansible.builtin.apt:
    name: auditd
    state: present

- name: Ensure auditd rules directory exists
  ansible.builtin.file:
    path: "{{ auditd_rules_dir }}"
    state: directory
    owner: root
    group: root
    mode: "0750"
```

```yaml
# ntp.yml
- name: Install chrony
  ansible.builtin.apt:
    name: chrony
    state: present

- name: Ensure chrony config directory exists
  ansible.builtin.file:
    path: /etc/chrony
    state: directory
    owner: root
    group: root
    mode: "0755"
```

## ADR-004

**Status:** Pending — to be written next session.

**Topic:** Terraform + Ansible for Proxmox VM provisioning vs manual VM creation.

**Decision preview:** Terraform (`bpg/proxmox`) owns VM lifecycle — create, destroy, resize. Ansible owns post-provision configuration — hardening, package state, service management. Cloud-init is scoped to bootstrap only: first user, static IP. Manual VM creation was rejected as it cannot be reproduced, version-controlled, diffed in review, or reliably destroyed and rebuilt.
