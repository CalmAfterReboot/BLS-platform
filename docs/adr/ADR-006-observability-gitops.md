# ADR-006 — Observability Stack Deployment via Standalone ArgoCD Application

| Field | Value |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-05-09 |
| **Project** | BLS Project 5 — Observability + Security |
| **Deciders** | BLS DevOps |

---

## Context

Project 5 introduces the observability layer for the BLS platform. The primary deliverable is kube-prometheus-stack deployed into the `monitoring` namespace, with a ServiceMonitor scraping the llm-gateway's `/metrics` endpoint.

Two architectural decisions required documentation:

1. **Why a standalone ArgoCD Application instead of the existing matrix ApplicationSet?**
2. **Why multi-source Application instead of a local Helm wrapper chart?**

---

## Options Considered

### Option A — Add monitoring to the matrix ApplicationSet

The existing ApplicationSet at `k8s/apps/app-of-apps.yaml` auto-discovers directories under `k8s/workloads/` and deploys them as Applications. Adding a `k8s/workloads/monitoring/` directory would bring kube-prometheus-stack under its management.

**Rejected.** The ApplicationSet template sets `path: '{{path}}'` as the Helm chart source — it expects a local chart directory in the repository. kube-prometheus-stack is an upstream chart published at `https://prometheus-community.github.io/helm-charts`. There is no supported way within the current ApplicationSet template to reference an upstream chart registry for a subset of workloads without restructuring the template for all workloads.

Workarounds (wrapper chart, forked chart in-repo) are explored and rejected below.

---

### Option B — Local Helm umbrella chart wrapping kube-prometheus-stack

Create `k8s/workloads/monitoring/Chart.yaml` with kube-prometheus-stack as a chart dependency. ArgoCD discovers it via the ApplicationSet and installs the umbrella chart.

```yaml
# k8s/workloads/monitoring/Chart.yaml
dependencies:
  - name: kube-prometheus-stack
    version: "84.5.0"
    repository: https://prometheus-community.github.io/helm-charts
```

**Rejected.** This approach requires:

1. Running `helm dependency update` locally and committing the `charts/` tarball to Git, or
2. Configuring ArgoCD to run `helm dependency update` before sync (requires Helm credentials and repo registration)

In practice ArgoCD does not automatically resolve chart dependencies from remote registries when it encounters a local chart. The result is a sync error unless the `charts/` directory is committed — which means committing a large binary blob that changes every chart update. This violates the intent of pinned, reviewable Git history and creates a maintenance burden on every version bump.

---

### Option C — Standalone ArgoCD Application with multi-source *(selected)*

Create `k8s/apps/monitoring.yaml` as an explicit `Application` resource (not generated by the ApplicationSet). Use ArgoCD's multi-source feature (available since ArgoCD 2.6) to combine two sources:

- **Source 1:** The upstream Helm chart at `prometheus-community.github.io/helm-charts`, pinned to `84.5.0`
- **Source 2:** The Git repository at `HEAD`, referenced as `$values`, providing the values override file at `05-observability-security/values/kube-prometheus-stack.yaml`

---

## Decision

**Deploy kube-prometheus-stack as a standalone ArgoCD Application using multi-source, with chart pinned to `84.5.0` and values sourced from the BLS-platform Git repository.**

---

## Rationale

**Standalone Application is the correct abstraction boundary.** The matrix ApplicationSet was designed for application workloads that share a uniform deployment model (local Helm charts, same sync policy). The observability stack is infrastructure — it installs CRDs cluster-wide, manages its own RBAC, and has a different lifecycle from application workloads. It belongs in `k8s/apps/` alongside the ApplicationSet, not under `k8s/workloads/`.

**Multi-source separates the chart from its configuration.** The upstream chart version is pinned in the Application spec. Custom values (homelab profile, disabled k3s control-plane scraping, resource limits) live in the Git repository as a reviewable YAML file. Bumping the chart version is a one-line diff in `monitoring.yaml`. Values changes are independently reviewable. Neither requires modifying the other.

**Chart version pinning is explicit and auditable.** `targetRevision: "84.5.0"` in the Application spec means every sync uses exactly that chart version. Drift is impossible without a Git commit. This satisfies the portfolio's public-repo quality standard and gives a clear upgrade path.

**`ServerSideApply=true` is non-negotiable for kube-prometheus-stack.** The CRD resources (PrometheusRule, AlertmanagerConfig, etc.) have annotations that exceed the 262144-byte limit enforced by client-side apply. Without `ServerSideApply=true`, ArgoCD will fail to sync with an annotation size error on first install and on every CRD update.

**k3s control-plane components are disabled in values.** k3s does not expose `kube-scheduler`, `kube-controller-manager`, `kube-etcd`, or `kube-proxy` on the standard endpoints that kube-prometheus-stack attempts to scrape. Leaving them enabled produces persistent `ScrapeError` targets in Prometheus UI and fires false alerts. Disabling them in values keeps the target list clean.

**`serviceMonitorSelector: {}`** is set to empty in the Prometheus spec so the Prometheus instance watches ServiceMonitors in all namespaces. Without this, the llm-gateway ServiceMonitor in the `llm-gateway` namespace would be invisible to Prometheus running in the `monitoring` namespace.

---

## Consequences

### Positive

- Chart version upgrades are a single-line Git diff — clear, reviewable, reversible
- Values file is independently versioned alongside the chart reference
- No binary blobs committed to Git
- Prometheus scrapes all namespaces — extensible to future workloads without values changes
- `ServerSideApply` protects against CRD annotation size failures on all future chart upgrades

### Negative

- Requires ArgoCD >= 2.6 for multi-source Application support. If the cluster runs an older ArgoCD, the Application will fail validation. Mitigation: verify ArgoCD version before applying; fall back to inlining values via `valuesObject` in the single-source spec if needed.
- Standalone Application is not auto-discovered by the ApplicationSet. Adding new standalone infrastructure Applications requires explicit files in `k8s/apps/` — intentional, but worth noting as a divergence from the fully-automated workload pattern.

---

## Alternatives Rejected

| Alternative | Reason |
|---|---|
| Matrix ApplicationSet for monitoring | ApplicationSet template assumes local chart path; upstream charts incompatible without structural changes to all workloads |
| Local Helm umbrella chart | Requires committing chart tarballs or Helm dependency runtime resolution; creates binary blob history |
| Single-source Application with inline `valuesObject` | Loses independent reviewability of values vs. chart version; large values blobs inside the Application spec reduce readability |
| Manual `helm install` outside GitOps | Breaks GitOps principle; no drift detection; no automated self-heal |

### Verification

```bash
# Confirm Application syncs
kubectl get application kube-prometheus-stack -n argocd

# Confirm Prometheus targets include llm-gateway
kubectl port-forward svc/kube-prometheus-stack-prometheus 9090:9090 -n monitoring
# open http://localhost:9090/targets — expect llm-gateway/0 (1/1 up)

# Confirm /metrics is reachable on the gateway
kubectl port-forward svc/llm-gateway-service 8000:8000 -n llm-gateway
curl http://localhost:8000/metrics | head -20
```
